## A1：三麻立直北单骑，拔完其余北后不能生成本人操作选项

定位：[KanActions.java:96](../src/main/java/dev/riichicraft/rules/KanActions.java#L96)，调用经过 [ThreePlayerRound.java:259](../src/main/java/dev/riichicraft/rules/ThreePlayerRound.java#L259) 和 `view()`。

复现使用完整 108 张实体牌序与真实接受动作：东家初始手牌 `123456p789s345s4z`，摸一万后切一万立直，等待北单骑；另外两家正常摸切；东家依次摸到、拔出另外三张北。第三次拔北已返回 `ACCEPTED`，补到九索，牌与点数守恒仍成立。此时本人手内一北、拔北区三北，不能求第五张北，实际等待为空。

`ThreePlayerHands.waits()` 正确排除了这张不存在的第五北；但 `KanActions.options()` 将“已成立立直的当前等待必须非空”视为永久前置条件，即使没有任何暗杠选项，也会抛出 `IllegalArgumentException`。本人视图和后续普通出牌均会经过这个查询，合法牌局因此不能正常继续。编码／解码该已接受状态成功，恢复后查询仍抛异常。

**修复方向：**保留已确认的“立直后仅拔新摸北”；让这种合法状态仍可生成正常操作选项，本复现场景应返回无可用杠。其他暗杠仍按已定的等待种类／枚数及送杠限制判断，不能由本次无杠例子推定新的禁杠规则。补完整后续摸切、他家行动、荒牌不听结算及恢复回归。单局与整场共用该核心，均应接入验证。

现有 `ThreePlayerEngineTests.riichiThenKita` 只覆盖一次拔北；另有“自持四北不算听”的独立测试，两者没有串成同一已立直轨迹。复现：[RiichiNorthExhaustion.java](audit/repro/RiichiNorthExhaustion.java)。证据属于实际独立规则核心执行，未声称进行了真人游戏内复现或证明整个 Minecraft 进程退出。

## A2：回大厅后遗留缺席玩家的座位

定位：[LobbyService.java:611](../src/main/java/dev/riichicraft/server/LobbyService.java#L611) 的终局返回，以及 [LobbyService.java:617](../src/main/java/dev/riichicraft/server/LobbyService.java#L617) 的主动终止分支。

牌局中断线／离椅时保留玩家身份是正确行为。但返回大厅只删除牌局、清断线标记、取消准备，没有重新执行大厅的缺席成员清理。断线者的乘坐记录已经删除，下一次 `refreshMounts()` 也无法再发现他。

原生服务端三组检查分别覆盖“活动局断线→终止”“结算后断线→返回大厅”“活动局离椅→终止”，每组均跑三麻／四麻真实大桌。六个分支均出现 `released=false, replacement accepted=false`：缺席者仍占座，新玩家右键对应空出的椅子被拒绝。如果缺席的是初始东位，也会阻止重新开局。

**修复方向：**建立统一返回大厅转换，释放离线玩家及实体桌上不再具有有效原椅乘坐的玩家，保留仍正常在座者，再取消准备、广播和保存。保持旧桌“仅关闭界面不离座”和活动局保留原身份的既定行为。回归应验证成员索引、可替补、东位开局和重复返回的幂等性。

复现：[AuditServerGameTests.java](audit/repro/AuditServerGameTests.java)。现有测试验证活动局保留身份和返回后取消准备，但部分用例先让断线夹具重新打开视图，因此未覆盖“真正缺席时返回”的转换。

## A3：操作层隐藏时，Esc 漏掉退出俯瞰

定位：[TableInteractionClient.java:45](../src/client/java/dev/riichicraft/client/TableInteractionClient.java#L45)、[TableScreen.java:503](../src/client/java/dev/riichicraft/client/TableScreen.java#L503)。

真实坐席中按 R 收起操作层，按 V 可在无界面时重新进入俯瞰。随后按 Esc 会进入原版暂停菜单，不经过 `TableScreen.onClose()` 的退出俯瞰逻辑；相机仍维持俯瞰，关菜单后也没有恢复。已有测试只覆盖操作层显示时的 Esc。

**修复方向：**将“退出俯瞰”作为桌面会话的键盘行为处理，覆盖操作层显示／隐藏状态，并保留聊天和其他菜单的输入边界。不要通过清除参赛身份或离椅来复位镜头。

定向复现：[AuditClientChecks.verifyEscapeFromHiddenOverhead](audit/repro/AuditClientChecks.java)。运行结果见[证据表](audit/README.md)。

## A4：打出的不是最右手牌时，动画来源位置不准确

定位：[TableAnimationPlayer.java:83](../src/main/java/dev/riichicraft/table/TableAnimationPlayer.java#L83)、[TableDisplayRenderer.java:101](../src/client/java/dev/riichicraft/client/TableDisplayRenderer.java#L101)。

公开动画只知道暗手张数及匿名槽位。手牌从 14 张变成 13 张时，消失的永远是最右 `h:seat:13`，新河牌便从此槽起飞。私有显示立即使用新手牌排序，未用上一帧所选实体牌的位置纠正动画来源。

确定性检查打出本人最左实体牌 0，上一帧 x 为 `-17.65`，新河牌动画 t=0 却从 x 约 `6.01` 出现，相差约 23.66 个模型单位。比较只用 x/z，排除了牌体高度和尺度差异。它影响视觉连续性，不改变权威手牌、出牌或计分。

**修复方向：**在本人／已获授权可见的手牌展示层保留上一局面实体牌与位置映射，纠正弃牌、吃碰来源；公开旁观背牌流仍可使用匿名槽。继续覆盖私有消息先到、动画积压、开新局、重连与每牌只显示一次。不要为动画发送未公开牌墙。

定向复现：[AuditClientChecks.verifySelectedDiscardOrigin](audit/repro/AuditClientChecks.java)。这是客户端实际帧函数的确定性夹具，不冒称某一真实牌局内已经完成全部动作的人眼验收。

## T1：恢复回归对终局的错误假设

本次未改源码的完整 TCP 基线在 [PersistenceClientScenario.java:157](../src/gametest/java/dev/riichicraft/test/PersistenceClientScenario.java#L157) 失败。测试恢复一个随机位置的部分响应窗口，随后无条件再推进一次动作，然后点击“终止／确认终止”。该次推进可能用完牌山并进入结算。

已查看该次原生截图 `0051_riichicraft-persistence-resumed.png`：画面实际为“荒牌流局”，按钮为“返回大厅”，此时终止按钮已隐藏。失败说明测试忽略了合法终局分支，不是生产终止失效或异步存档问题。该断言只检查 `snapshot.game == null`，文案却同时声称清除了存档，也应补真正的归档读取验证。

**本轮已修正测试：**根据实际终局走“返回大厅”或二次终止，等待服务端确认后分别检查客户端、服务端内存与磁盘归档的清理。保留全部原有恢复／原响应断言，没有忽略失败。后续仍建议用固定的非末次恢复轨迹单独保证该场景的终止按钮覆盖；现有其他客户端场景已有实际二次终止路径。本次最初失败日志保留，不能用后续一次随机通过将其掩盖。

## 可读性、鲁棒性与重构顺序

### 1. 先冻结存档兼容样本

[FourPlayerRound.java:389](../src/main/java/dev/riichicraft/rules/FourPlayerRound.java#L389)、[ThreePlayerRound.java:434](../src/main/java/dev/riichicraft/rules/ThreePlayerRound.java#L434) 等使用 record 默认 `toString()` 作为重放指纹输入。字段／类型重命名也可能使正常旧档指纹不同。现有版本检查与失败保护有效，这不是已证实的当前存档破坏；但它是安全重构的前置约束。

先提交本版三／四麻的活动局、部分响应、局间和终局历史字节夹具与预期摘要，确保“旧版写、后续版本读”一直通过。现有同版生成／同版读取、甚至跨 JVM 测试不能替代这一保护。首轮提取代码保持指纹及二进制格式不变；显式稳定编码或迁移作为独立工作讨论。

### 2. 拆开服务端转换与快照投影

`LobbyService` 为 1,270 行，同时负责大厅、四类核心实例、六种赛制入口、坐席、暂停、存档、私有快照、旁观动画、声音和短等待。A2 正是分散生命周期转换容易遗漏清理的例子。

建议依次抽出统一生命周期转换、纯快照转换、存档协调。`Prototype` 的四个可空核心字段隐含“恰好一个有效”，可用有明确类型的适配接口收束；初次抽取保持规则和外部格式不变。不要先合并两套完整 Round 状态机。

### 3. 共享新旧界面的展示转换

`TableScreen` 为 659 行，混合选牌、双击、动作分组、菜单、帮助／历史、结果分页和点差计算；`GamePanel` 同时维护另一套结果与动作标签。先抽出共用的结果／动作展示模型，让两个界面保留自身布局与输入，避免一边修复而另一边遗漏。

相机生命周期与几何投影也可分开；以帧测试保护后再优化。保留旧桌兼容入口，不进行整套 UI 重写。

### 4. 小块收束三麻／四麻重复

两份立直状态各 127 行、杠状态各 91 行、账本各 231 行、归档编解码各 223 行，整场规则也高度平行。已经有三麻死分支仍保留四麻 `%4`、三麻注释沿用 750 点四麻例子的复制残留，虽未造成当前合法对局错误，也会提高双边修复成本。

优先抽取受限 I/O、支付／守恒、投票和具名配置等公共小块，显式保留拔北、不同牌墙／补牌及三麻支付。每个提交只重构一个职责，并对照既有固定轨迹和旧档样本；不要把规则变更与重构混在同一提交。

### 5. 格式、边界和诊断整理

104 个生产 Java 文件共 12,451 行，其中 140 行超过 160 字符，13 行超过 240 字符。长行只是定位信号：真正的问题是多语句、分支和重复转换挤在同一行，尤其 `GamePanel`、两套 Round、协议和动画代码。按模块整理格式、命名常量和失败原因，比一次全仓库格式化更易核对。

模式 `%3`／`>=3`、跨层 `ordinal()` 和同名 `Status.valueOf()` 是未显式写出的契约。建议内部具名类型及明确映射；第一轮不改现有网络／存档编号。部分 DTO 虽有分配上界，跨字段一致性校验仍不齐全；可集中整理，但本次没有由此复现生产越权或无界分配。

存档失败日志目前不带捕获异常原因，管理员难以分清校验、重放还是文件系统问题。保留原字节／失败封锁行为，同时记录异常链；面向玩家继续显示简短信息。

### 6. 性能先测量再处理

一次实体桌广播为每个接收者重新构造所有人的 `gameView()`，随后又构造接收者本人快照。N 个仍订阅实体会话视图的参与者、M 个显式观战视图时，同一当轮动作分析约重算 N+M+1 次；相机每帧也有重复投影。可考虑按核心修订缓存不可变选项、构造一次私有源再按身份投影、每帧复用投影结果。

**本次未做多桌性能基准，没有证据称其已经导致 TPS 或帧率下降。**普通公共快照用空接收身份，不会同样求当轮私有动作，不能泛称每 tick 都重算所有玩家评分。性能缓存必须保留身份隔离和正确失效边界。
