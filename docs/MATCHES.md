# 四人东风／半庄整场（开发中）

更新：2026-10-17。当前分支 `codex/four-player-matches`，版本 `0.0.5-dev`。本文件记录正在实现的整场功能；上一个完整验证的四人单局见 [SINGLE_ROUND.md](SINGLE_ROUND.md) 和 [VALIDATION.md](VALIDATION.md)。

## 已确认的交互与生命周期

用户已确认以下流程：

- 大厅保留单局，增加东风与半庄。初始东位选择赛制、开局，起家沿用自动入座的初始东位；改变赛制清空全员准备。
- 整场保持原来的四个桌位，按当前庄家计算自风；轮庄不交换玩家身份或座位。
- 小局结算后保留结果、牌河、点数和供托。四人各自确认继续，第四人确认才创建下一小局；有人缺席就清空续局确认。关闭界面不退出整场。
- 活动小局仍沿用缺席暂停、四人重新确认恢复；局间续局确认与活动局恢复确认分开处理。
- 整场中途终止仍需客户端二次确认。整场结束后，任一参与者可带全桌返回大厅，取消准备；重新开场才重置为四家各 25,000 点。
- 破桌、区块卸载、停服仍清理临时对局。本步骤没有增加保存、跨重启恢复、机器人或倒计时。

## 代码分工与进度

- `MatchRules`：独立于 Minecraft 的轮转政策和最终排名计算。排名按最终点数降序，同点按起家时的东南西北顺序；剩余供托归发放前确定的首位。25,000 返、顺位马 +15／+5／−5／−15，得分以 0.1 为单位精确计算。
- `FourPlayerMatch`：独占当前真实 `FourPlayerRound`，从已经关闭的小局账本读取点数／供托及结束事件。原小局账单保持不可变，最终剩余供托单独记在整场结果，不重写旧收据。
- 每小局使用新 UUID，继续票绑定整场 UUID、小局 UUID 和确认批次。玩家缺席时推进确认批次，使旧票失效；同批次其他人的确认不使合法票过期。
- 第四票先创建并验证完整新局，再替换旧局；失败应保留已付账结果与前三票。服务端工厂交付新局后不得继续持有并修改它，公开 UUID 与秘密洗牌种子独立生成。
- 大厅、网络、服务端与界面的赛制选择、续局、场风／本场和最终排名代码已落盘。东风只允许至南四，半庄只允许至西四的公开局号。
- **整场推进政策尚未定稿，当前工作区不能作为可用整场版本构建／发布。** `MatchRules.afterRound` 尚未实现，完整规则入口、构建与游戏回归尚未运行。已有测试文件不等于测试已通过。

## 待用户裁定的三处边界

这些问题已在本次设计沟通中提出，尚未收到答复；以下是建议而非已确认规则：

1. **本场推进**：庄家和牌本场 +1；仅闲家和牌清零；荒牌、途中流局和流局满贯都 +1，荒牌即使轮庄也保留递增值。途中流局只连庄，不触发听牌止。
2. **延长骤死优先级**：每次完整小局结算后有人达到 30,000 就结束，唯多响包含庄家时优先连庄；该场末局若庄家已首位且达标，仍按自动和了止／听牌止结束。需明确是否实际要扩大为所有庄家连庄均优先。
3. **最大末局仍未达标**：东风最多南四，半庄最多西四；建议庄家和牌／荒牌听牌仍可在原局连庄，庄家不连庄时结束，绝不进入下一场。需明确是否改为最大末局无条件结束。

普通雀魂基线及用户之前的单局裁定见 [FOUR_PLAYER_RULES.md](FOUR_PLAYER_RULES.md)。本次重新获取的 [官方规则](https://mahjongsoul.com/news/46) 与 [FAQ](https://mahjongsoul.com/faq) 未给出上述所有组合的完整事件例子；不能把建议写成新找到的官方判例。
