# Riichicraft 项目规划

日期：2026-10-15。

状态：设计草案。用户已确定平台、初期与长期目标，以及“实体麻将桌＋手牌操作界面”的交互方向；下文的具体规则参数与版本划分属于建议，可在相应阶段开始时调整。

## 1. 项目目标与开发原则

近期目标是让朋友们在 Minecraft 世界里坐到同一张桌旁，完成规则清楚、结算可靠的日本麻将对局。首个玩法发布目标覆盖：四人东风、四人半庄、三人东风、三人半庄。

长期目标是让麻将成为探索与故事的核心玩法：遇见角色、发现雀庄或遗迹、通过对局推进任务，最后进入有独特生态与剧情的维度。

执行原则：

1. 每次只推进一个可展示、可验证的小步骤。
2. 先建立可靠的对局流程，再丰富模型、动画和世界内容。
3. 四麻先完成，三麻作为独立规则预设扩展。
4. 普通桌、自动桌、NPC 对局和剧情对局共用规则核心。
5. 初期按真人多人对局规划。NPC 补位放在后续阶段；单人世界早期可摆桌和调试，完整开局仍需足够参与者。
6. 使用原创或明确允许使用的牌面、模型、声音和文本；发布前整理素材来源及许可证。

术语约定：“一小局”指从配牌到一次和牌或流局；“一整场”指按东风／半庄规则完成的比赛，包含连庄与可能的流局，不等于固定打四次／八次。

## 2. 第一版的玩家体验

目标流程：

1. 放置麻将桌，右键打开桌子界面。
2. 选择座位、规则预设和赛制；参与者准备。
3. 满足人数与准备条件后开局，由服务器洗牌、配牌并管理牌山。
4. 玩家在手牌界面中选牌，通过明确按钮完成出牌、吃、碰、杠、立直、自摸、荣和或跳过。
5. 世界桌面逐步展示牌背、牌河、副露、宝牌指示牌和场况；界面始终能看清公共信息。
6. 小局结束显示役、番、符、支付明细及分数变化；继续下一局。
7. 整场结束显示最终点数、排名和结束原因，返回大厅。

手牌界面应优先支持清楚的牌面、摸牌区分、选中反馈、动作提示和多种吃／杠选择。出牌采用选中后确认的初始方案，快捷操作在实测后再加入。

其他玩家和旁观者只能得到其有权看到的信息。隐藏手牌和未公开牌山不发送给他们；客户端只渲染牌背不足以保护信息。

## 3. 物品与方块如何分批加入

| 内容 | 最早用途 | 扩展方向 |
| --- | --- | --- |
| 普通麻将桌 | 第一个世界交互入口，随后承载大厅和对局 | 材质变体、完整桌面、可选座椅 |
| 麻将牌／牌盒 | 支持完整牌面和一副牌的概念 | 独立牌具物品、摆放、收藏与牌背 |
| 点棒 | 先以界面数值表达分数；首个玩法发布前补基础物品 | 实体展示、收纳、不同材质 |
| 骰子 | 服务器产生掷骰结果，展示用于开局的规则结果 | 独立使用、声音与滚动演出 |
| 起家／场风标记 | 以界面标记起步 | 桌面立体标记 |
| 自动麻将桌 | 对局系统稳定后加入 | 洗牌与升牌演出、电子点数显示、便利操作 |

早期普通桌由系统协助洗牌、发牌和结算。自动桌的具体差异在该阶段设计，以交互与演出为主，仍采用同一套公平规则。

牌局中的牌是服务器内部的牌实例，包含牌种、赤牌属性和唯一标识。牌具物品是另一层表现；对局不靠把一百多件可拾取物品撒在世界里推进。可以用一个麻将牌物品类型配合数据区分牌面，具体注册方式在实现时确定。

牌局点数由服务器账本管理。点棒物品用于牌具体验，其数量不直接决定对局分数。第一版不引入跨世界货币兑换；今后若要兑换，另行设计存取和防重复结算。

## 4. 规则范围与预设

### 4.1 四麻先完成一份固定预设

建议初始预设采用：每人 25,000 点、食断有、后付有、三张赤五、常规役种及役满。赤五替换对应普通五，不额外增加整副牌的张数。

这是 Riichicraft 的待定预设，并非宣称完全复刻某个平台或赛事。应维护一份带版本号的规则表，正式支持的规则都要有明确行为及验证样例。

一个可对外称为“四人日麻可玩”的版本至少要覆盖：

- 配牌、轮流摸打、牌山和王牌、宝牌与里宝牌。
- 吃、碰、明杠、暗杠、加杠，以及多人响应时的优先级。
- 立直条件、立直后的操作限制、一发及其失效、抢杠与岭上流程。
- 标准和牌形、七对子、国士无双；无役不能和牌，宝牌本身不构成役。
- 舍牌振听、同巡振听、立直振听。
- 声明支持的役种、番符计算、庄闲荣和／自摸支付和上限规则。
- 荒牌流局、听牌罚符、途中流局、流局满贯，以及与所选预设相符的边界。
- 连庄、轮庄、本场、立直供托、场风变化及整场结束与同分排序。

规则工作可拆批开发，但尚未支持上述主要规则时应标为“开发原型”。不能用“只允许自摸”或“只实现少数役”代替完整玩法验收。

以下差异在规则核心阶段开始时逐项写定：

| 决策点 | 建议处理 |
| --- | --- |
| 多人荣和 | 先确定双响／三响、头跳及供托归属，再实现响应裁决 |
| 途中流局 | 明确九种九牌、四风连打、四家立直、四杠散了等条件与例外 |
| 杠相关 | 明确立直后暗杠、国士抢暗杠、新宝牌公开时机及包牌 |
| 打点 | 明确切上满贯、累计役满、复合／双倍役满等选项 |
| 整场结束 | 建议首期无目标点数延长；明确飞人阈值、末局连庄及和了止 |
| 结果排名 | 先显示原始点数及确定的同分排序；返还点、顺位马点另列选项 |

先形成少量固定预设，再增加配置项。每场开局保存规则快照，进行中不切换规则。

### 4.2 三麻是一套独立预设

建议以去除二至八万、不可吃、使用拔北的常见方向起草三麻规则；最终行为需单独写定。

必须处理：

- 三人用牌、赤牌数量、座位与庄家轮转、万子宝牌指示关系。
- 拔北时机、是否可保留北作手牌、补牌来源、补牌耗尽。
- 拔北对一发及相关役的影响，拔北可否被荣和。
- 三麻自摸采用自摸损还是补偿支付，本场与供托如何结算。
- 起始点数、流局罚符、多人荣和、途中流局及整场结束。

三麻东风和半庄分别做整场验收。人数变化不能仅由“第四个座位为空”实现。

## 5. 技术结构：为扩展保留边界

初期使用一个 Fabric 工程，在代码中分清职责；规则核心保持不依赖 Minecraft 类，以便快速单独运行测试。

按客户端与服务端都安装 Riichicraft 规划，早期要求双方使用相同模组和规则协议版本。单人／局域网与专用服务器共用服务端规则路径。

```text
手牌界面／世界桌面／将来的 NPC
              ↓ 动作请求
Fabric 服务端：座位、权限、网络与存档
              ↓ 合法动作
Java 规则核心：牌、牌局状态、和牌、计分与整场轮转
              ↓ 状态变化与结果
按玩家权限生成视图 → 界面、桌面与将来的任务系统
```

建议边界：

| 部分 | 职责 |
| --- | --- |
| 规则核心 | 牌实例、规则快照、合法动作、状态转换、役／符／分、局与场 |
| 服务端对局管理 | 桌子与座位、玩家 UUID、动作顺序、响应窗口、生命周期 |
| 网络 | 公共与私人视图、动作请求和拒绝原因、重连同步 |
| 世界内容 | 桌子、牌具、方块实体、后续自动桌及生存配方 |
| 客户端 | 手牌界面、公共场况、桌面渲染、声音与动画 |
| 后续内容 | NPC 决策、结构、维度、任务与剧情数据 |

网络只接收“我要做什么”。服务器依据玩家身份、座位、当前阶段、牌局版本和合法动作验证请求；客户端不能提交自己的点数或和牌结论。每张桌子独立编号，过期或重复请求不能推进第二次动作。

建议状态流程：大厅 → 开局／配牌 → 自家操作 → 等待他家响应 → 裁决 → 下一操作，或进入小局结算 → 下一局／整场结算。所有可能产生鸣牌／荣和的流程都通过显式响应窗口裁决，不能由网络消息抵达先后决定胜负。

存档至少包含数据版本、桌子标识、规则快照、玩家与座位、完整牌局状态、分数／供托、本场和动作序号。调试种子、完整手牌及牌山只保存在服务端；公开日志不泄露这些信息。

正常重启应能恢复到暂停状态，由原参与者确认后继续。异常崩溃最多恢复到最近成功保存的快照，具体保证在存档实现后验证并记录。

后续剧情通过“小局结束／整场结束／任务目标达成”等事件推进，普通对局仍然可以独立游玩。剧情特殊规则另设预设并在开局明示。

## 6. 分阶段路线

版本号用于表达先后顺序，不是交付日期。每行仍可拆成多次小改动。

| 阶段 | 玩家可看到的成果 | 主要验收 |
| --- | --- | --- |
| v0.0.1 工程与基础桌 | 模组能加载；有一张可放置、破坏、交互的桌子 | 客户端与专用服务器启动；桌子和资源正常 |
| v0.0.2 入座大厅 | 四个逻辑座位、准备／取消、开始条件提示 | 多人入座不冲突；退出可处理；两桌互不干扰 |
| v0.0.3 摸打原型 | 发牌、手牌界面、轮流摸打和公共牌河 | 固定种子可复现；牌不丢不重；越权／重复动作被拒绝 |
| v0.0.4 四人单局 | 吃碰杠立直、和牌／流局与自动结算 | 固定预设主要规则完整；样例打点与真实多人流程通过 |
| v0.0.5 四人东风 | 连庄、轮庄、供托、本场和整场结果；存档恢复 | 完整东风战；断线重连、正常重启与区块卸载验证 |
| v0.0.6 四人半庄 | 同一核心支持南场和整场结束 | 实际完整半庄；末局与同分边界用定向场景验证 |
| v0.0.7 三麻 | 拔北、三麻支付、三麻东风／半庄 | 三麻差异样例通过；两种赛制实际完成 |
| v0.1.0 首个玩法发布 | 四种模式、基础牌具物品、可读桌面与界面 | 四模式验收、多人稳定性、规则说明和已知限制齐全 |
| v0.2 生存与自动桌 | 配方、自动麻将桌、牌具展示、基本音效与动画 | 生存获得流程可用；普通桌／自动桌结算一致 |
| v0.3 NPC 与教学 | 基础 NPC 对手、可理解的教程、单人对局入口 | NPC 只看允许信息，只选合法动作，可完成整场 |
| v0.4 结构与短任务 | 一个小型雀庄／遗迹、一名关键角色、一条短任务 | 探索→对局→推进→奖励的短流程可完成并能续档 |
| v0.5 维度样板 | 一个可往返的小型维度区域和一个剧情章节 | 进入、探索、对局、退出、多人及存档恢复正常 |
| v1.0 大型内容发布 | 根据样板扩展区域、结构、角色和完整主线 | 全主线可完成；老存档迁移及多人任务行为验证 |

v0.0.4 内部再按“和牌判定与计分 → 响应裁决与副露 → 立直和杠的边界 → 流局规则”拆任务，避免一次实现所有规则。

NPC 首先采用简单可解释策略，后续根据体验提高强度。机器学习与外部 AI 服务属于可选研究方向，不作为剧情或单人游玩的前置条件。

## 7. 生命周期的建议默认行为

以下行为在对应多人阶段实现，并在正式发布前验证：

- 关闭操作界面保留座位，可再次右键打开；已经触发的响应窗口仍按规则处理。
- 正常对局按阶段推进，不每 tick 全量广播。响应计时使用统一服务端时钟，暂停期间不计时。
- 训练／朋友局初期不设强制出牌倒计时；响应窗口超时按跳过处理，时长在大厅可见。
- 参与者掉线、死亡、离开允许范围或切换维度时暂停并保留状态，返回后恢复同步；暂不自动判负或由 NPC 接管。
- 开局后保护桌子，防止普通破坏导致状态丢失；管理员可明确终止对局并释放所有座位。
- 桌子区块卸载时保存并暂停，重新加载后等待恢复；初期不强制长驻区块。
- 玩家使用 UUID 关联座位；每名玩家同时只参与一桌，旁观权限与参赛权限分别处理。
- 结算只提交一次，点数与供托满足守恒，未完成的对局不产生最终胜负奖励。
- 整场结束或明确终止后清理本场状态和占座，桌子能够重新开局。

首个发布前需要验证“当前网络条件下的公平响应”。响应时间不能因客户端动画或低帧率而缩短；暂停和重连不会重复触发已经完成的声明。

## 8. 怎样确认每一步真的完成

规则／离线验证：

- 固定牌山与动作序列，覆盖和牌形、役／符／分、振听、鸣牌竞争、立直后操作及三麻差异。
- 牌实例分布守恒；每张牌恰好位于一个合法区域；动作前后手牌结构合法。
- 分数与供托守恒；同一次结果重复处理不重复扣分。
- 保存／读取后，待响应阶段、合法动作与视图保持一致。

Minecraft 实测：

- 在指定的 26.2 Fabric 客户端和专用服务器运行，不以编译通过替代服务器测试。
- 真人或受控测试客户端分别完成四麻东风、四麻半庄、三麻东风、三麻半庄。
- 定向验证同时响应、多桌、重连、正常重启、区块卸载及桌子受破坏的处理。
- 检查非本人客户端实际接收的数据中没有隐藏手牌／牌山信息。

玩家体验验收：牌能看清，按钮不歧义，错点能预防，结算能解释，长时间游玩不会因界面或视角难受。自动化客户端和静态检查不能替代这部分反馈。

每次交付记录“本次实现、离线验证、游戏实测、尚待验收”。本节保留整个项目的验收要求；当前步骤已执行的检查以 [VALIDATION.md](VALIDATION.md) 为准。

## 9. 开始实现前的最少决策

第一个开发步骤只需落实 Minecraft 26.2 对应的具体工具链、Java 包名与基础桌交互；见 [FIRST_STEP.md](FIRST_STEP.md)。

进入规则核心前，再确定四麻和三麻规则表。进入生存、NPC、世界生成和剧情阶段时，再分别讨论配方、美术方向、难度、世界设定和叙事，避免过早固定尚未验证的内容。

首次工程建立后记录可复现的构建命令、锁定版本和运行方式。后续维护使用小改动和明确验收；Minecraft 跨版本迁移单独规划，不随功能改动自动升级目标版本。

2026-10-15 核对了以下官方资料。工程与固定依赖组合随后已通过构建、服务端及客户端测试，实际版本和证据分别见 [DEVELOPMENT.md](DEVELOPMENT.md) 与 [VALIDATION.md](VALIDATION.md)。

- [Fabric 的 Minecraft 26.2 说明](https://www.fabricmc.net/2026/06/15/262.html)：26.2 的工具链、注册与 GUI 等变化。文中版本是发文时的建议，实际搭建时重新选择兼容组合并锁定。
- [Fabric 工程创建指南](https://docs.fabricmc.net/develop/getting-started/creating-a-project)：以官方模板建立目标版本工程。
- [Fabric 网络指南](https://docs.fabricmc.net/develop/networking)：客户端／服务端通信和服务端校验。

26.2 涉及渲染后端变化；自定义桌面渲染应使用游戏支持的渲染抽象，避免依赖原始 OpenGL 调用。初期采用简化模型，有利于先验证对局体验。
